This file is the single, tool-agnostic entry point for any AI coding agent working
in this repository (Claude Code, OpenAI Codex, Cursor, GitHub Copilot, or any other
agent that reads `AGENTS.md`). Read it before making changes.

Repo-local Codex skills also exist under `.codex/skills/` with the same content

## Hard rule: no autonomous git commit/push

**Never run `git commit`, `git push`, or otherwise publish changes on your own
initiative.** Make the requested code changes, leave them uncommitted in the
working tree, and tell the user what changed and why. Only commit or push if the
user explicitly asks for it in that turn. This applies to every agent and every
session, with no exceptions for "small" or "safe" changes.

## What the project does

Proxmox Backup Orchestrator is a specialized control plane for rotating
external-disk backups in a small Proxmox VE + Proxmox Backup Server (PBS)
environment. The web UI and API live in one native Debian 13 LXC (documented
install; the Docker Compose app VM is the legacy path); USB passthrough and
disk discovery stay behind a root agent on the Proxmox host, and PBS datastore
actions go through the PBS REST API (`PBS_MODE=api`) or, legacy, a PBS root
agent.

Core workflow:

1. Detect an eligible external disk on the Proxmox host.
2. Pass that USB device through to the PBS VM.
3. Prepare or reuse a PBS datastore on the external media.
4. Sync backups from the main PBS datastore to the removable datastore.
5. Safely eject the disk (unmount on PBS + remove USB passthrough).

The same control plane also covers inventory sync, backup visibility, planning
(scheduling), notifications, and maintenance operations around that workflow.

Current constraints (do not silently "fix" these — they are intentional unless a
task asks you to change them):

- Single-admin, admin-driven product. Accounts live in the `users` table but
  there are no roles/permissions: the first (and only) admin is created by
  `POST /api/v1/setup/admin` (refused once an account exists) or imported once
  from a legacy `AUTH_USERNAME` / `AUTH_PASSWORD_HASH`. Authentication cannot be
  disabled (`AUTH_ENABLED` no longer exists). See "Configuration & auth model".
- The backup flow is specialized for removable-media PBS replication, not a
  generic backup orchestrator.
- Real privileged operations depend on the host and PBS agents running with
  root-level capabilities.
- PBS-native export behavior depends on `proxmox-backup-manager` and real PBS
  host semantics.
- `Makefile` targets `install`, `dev`, `lint`, `test` are placeholders (`@echo`).
  Use the per-app commands below instead.

See `ROADMAP.md` for planned/known-missing work (CI, e2e tests, multi-user,
auto-eject gaps, etc.) before assuming something is unimplemented by accident.

## Architecture

```text
Browser
  |
  v  https://<lxc-ip> (443, self-signed)
LXC "pbo" (Debian 13, scripts/install/pbo-install.sh)
  pbo.service = uvicorn (user pbo, HTTPS 443)
    - apps/api  -> FastAPI control plane, also serves apps/web/dist
  PostgreSQL (localhost only)
  `update` = scripts/install/pbo-update.sh
  |
  | HTTPS, agent cert pinned, per-agent token (pairing-code registration)
  v
Proxmox host root agent (/opt/pbo-agent, AGENT_ROLE=host, vmbr0 IP:8090)
  - disk discovery
  - disk preparation helpers
  - QEMU USB passthrough attach/detach
  - maintenance endpoints for the host-side agent checkout
  |
  | USB passthrough
  v
PBS VM: REST API (PBS_MODE=api), or legacy PBS root agent
  - inspect visible disks
  - prepare dedicated PBS datastore
  - run PBS-native sync/export operations
  - safe eject / cleanup helpers
```

Default ports: LXC `443` (HTTPS, API **and web UI**: the API serves the built
`apps/web/dist` itself, same origin — no CORS); legacy Docker app VM `8000`,
app maintenance agent `8092`; Proxmox host agent `8090`, PBS agent `8091`.
`5173` is only the local Vite dev server (`npm run dev`, proxies `/api` to
`localhost:8000`). Agent ports are meant to be tightly firewalled — only the app
should reach them — and every call is additionally protected with an
`X-Agent-Token` header.

## Configuration & auth model (read before touching settings or auth)

- **Two kinds of settings** on the `Settings` dataclass
  (`apps/api/app/core/config.py`):
  - *Bootstrap / env* (read from the environment only): `APP_ENV` (default
    `production`), `DATABASE_URL`, `AUTH_SECRET_KEY`, `AUTH_COOKIE_SECURE`,
    `DEV_SEED`, `WEB_DIST_DIR`, `PBO_TLS_CERT_FILE`, `PBO_AGENT_SOURCE_DIR`,
    `PLANNING_SCHEDULER_*`, `EXTERNAL_BACKUP_LEGACY_COEXISTENCE_ENABLED`,
    app-maintenance-agent vars. In the LXC they live in `/etc/pbo/pbo.env`
    (0600, generated by the installer).
  - *Operator settings* (Proxmox/PBS URLs+tokens+fingerprints, PBS VM id/node,
    PBS datastore, agent URLs/tokens/timeouts, callback URL, ntfy, `NOTIFY_ON_*`,
    sync intervals, session lifetime): stored in the `app_settings` table. The
    registry is `SETTING_SPECS` in `apps/api/app/services/settings_service.py`
    — **adding one means a `Settings` field with a static default AND a spec
    entry** (an import-time assert checks they match). Secrets are Fernet-
    encrypted with a key derived (HKDF) from `AUTH_SECRET_KEY`
    (`app/core/security.py`) and never returned by the API.
- `get_settings()` = env base overlaid with stored values once
  `activate_settings_store()` ran at startup; the cache is invalidated on every
  write (`update_settings`). Code keeps reading `settings.<field>` — do **not**
  add new `os.getenv` reads for operator settings. Unit tests that don't run the
  lifespan get the env-only base, and keep patching `get_settings` per module.
- A legacy `.env` holding operator keys is imported **once** on first start
  (`import_settings_from_env`, marker row `meta.env_import_done`); afterwards
  `.env` edits to those keys have no effect — change them via
  `/api/v1/settings` or `/api/v1/setup/{proxmox,pbs}`.
- Startup order (`apps/api/app/main.py` lifespan): validate `AUTH_SECRET_KEY`
  → `create_tables()` (legacy tables) → Alembic `run_migrations()` (tables in
  `ALEMBIC_MANAGED_TABLES`: `users`, `app_settings`, `agents`,
  `agent_pairing_codes`, `setup_progress`) → env import + legacy admin
  import → activate settings store → `DEV_SEED` demo data → scheduler.
  New tables should be Alembic migrations in `apps/api/app/db/migrations/versions`.
- Sessions: login (`POST /api/v1/auth/token`) and first-admin creation set an
  `HttpOnly; SameSite=Lax; Path=/` JWT cookie (`pbo_session`), `Secure`
  unless `AUTH_COOKIE_SECURE=false`. No Bearer header, no token in JS storage.
  `get_current_user` also checks the account still exists and refuses
  cross-site writes (`require_same_origin`). Never add a state-changing GET.
- Public (no session) API surface: `/health`, `/api/v1/auth/{token,logout}`,
  `/api/v1/setup/{status,admin}`, `/api/v1/agents/register` (pairing code),
  agent callbacks guarded by `X-Agent-Token`, and two root routes:
  `/agent/install.sh` + `/agent/agent.tar.gz` (agent installer, no secrets)
  and `/calendar.ics?token=` (planning feed, own token, 404 when wrong).
  Everything else, including `/api/v1/setup/{proxmox,pbs}[/test]` and
  `/api/v1/settings`, sits behind the session (`protected_router`).
- TLS pinning (`app/core/tls.py`): `PVE_FINGERPRINT` / `PBS_FINGERPRINT` are
  checked inside the TLS handshake of **every** request of `ProxmoxClient`,
  `PBSClient` and the setup probes (`PinnedSSLContext.wrap_socket`), before
  the token is sent. Any new httpx client towards PVE/PBS must use
  `build_tls_verify(...)`, never a bare `verify=False`. Without CA nor pin the
  setup probe only returns the fingerprint (`trust_required=true`).

## Agents: pairing, tokens, pinning (read before touching agent auth)

- One-line install: `POST /api/v1/agents/pairing` (session) → single-use code,
  15 min, only its SHA-256 stored → the operator runs the command on the PVE
  host → `app/agent_install/install.sh` (served with the app URL baked in,
  validated as a plain https origin) installs the agent from
  `/agent/agent.tar.gz` (built from `apps/agent` of the running app) and calls
  `POST /api/v1/agents/register` (`services/agent_registry.py`).
- Per agent: **agent token** (app → agent, `X-Agent-Token`, Fernet-encrypted in
  `agents.token_encrypted`) and **callback token** (agent → app, SHA-256 only).
  Never accept one for the other. The agent certificate fingerprint is pinned
  on every app → agent call (`HostAgentClient(fingerprint=…)`, pin-only:
  `build_tls_verify(False, fp)`); the agent pins the app certificate
  (`AGENT_API_FINGERPRINT`, `PinnedAppSSLContext` in `apps/agent`).
- Registered agents reach the code through the settings overlay:
  `load_all_overrides()` puts `host|pbs_agent_base_url/_token/_fingerprint`
  on `Settings` (they are NOT `SETTING_SPECS`). A non-empty
  `*_agent_fingerprint` means "registered agent": `_callback_payload` then
  sends no token/URL (the agent uses its own), and the static token of that
  role stops being a callback credential. Static `.env` tokens keep working for
  roles without a registered agent (legacy).
- One active agent per role: a new registration revokes the previous one.

## First-run wizard (read before touching setup, auth redirects or the new UI)

- `/setup` (web: `apps/web/src/setup/`, API: `routes/setup.py` +
  `services/setup_wizard.py`): admin → host agent → Proxmox VE → PBS → done.
  Until `setup_completed` (`GET /api/v1/setup/status`) is true, the UI
  redirects every page to `/setup` (`setupRedirect` in `setup/logic.ts`). An
  install with a stored PVE connection and no `setup_progress` row (upgrade)
  counts as completed.
- `setup_progress` (single row) stores the step and **non-secret** results;
  `sanitize_progress_data` drops secret-looking keys. Tokens only go to
  `app_settings` (encrypted).
- PVE access: the host agent's `POST /pve/provision-access`
  (`apps/agent/src/agent/pve_access.py`, host role) runs `pveum` to create
  `pbo@pve`, role `PBO`, ACL `/` (user + token), and re-creates
  `pbo@pve!pbo`; it returns the secret and the PVE certificate fingerprint
  read locally (pinned, no TOFU). `PBO_PRIVILEGES` there and
  `PVE_PRIVILEGES` in `setup_wizard.py` must match (a test checks it); every
  privilege is justified in `docs/PERMISSIONS.md` — update it with any new
  `ProxmoxClient` call.
- PBS access: `POST /api/v1/setup/pbs/provision` (`services/pbs_provisioning.py`)
  takes the root@pam password once (pydantic `SecretStr`), gets a ticket over
  a connection pinned on the operator-confirmed fingerprint, creates
  `pbo@pbs` + `pbo@pbs!pbo` and the `PBS_ACLS` (user + token), refuses
  PBS < 3.3 before any change. The password must never reach a log, an error
  message, an exception chain (`from None`) or the database (tests check all
  four). Failed attempts are rate-limited (5 / 15 min / client).
- New UI stack (Tailwind 3 + shadcn/ui on Radix + lucide-react + Geist) is
  limited to the wizard: Tailwind only scans `src/setup` and
  `src/components/ui`, every utility is scoped under `#pbo-wizard`
  (`important`), preflight is off, rem values are converted to px, and there
  is no autoprefixer — the legacy `styles.css` output must stay
  byte-identical. Tokens are CSS variables in `src/setup/wizard.css` (dark +
  light). The wizard is a lazy chunk (`App.tsx`). Avoid Radix components that
  portal outside `#pbo-wizard` (Select, Dialog…) unless the portal container
  is set inside it.
- Command blocks for hosts have **no copy button** (uBlock "ClickFix").

## Language, time zone, PBS address, firewall (Phase 4.2)

- UI language: English by default, French available (`src/language.ts`).
  Precedence: account preference (`users.language`, Alembic `0004`,
  `PUT /api/v1/auth/me/preferences`, returned by `/auth/me` and login) >
  localStorage `pbo:language` > browser language on the very first load
  only. Held by `AuthContext` (`language`, `setLanguage`), used by the wizard
  and the legacy app. No UI text in code: `tests/language.test.ts` flags JSX
  text / aria-label literals in the wizard, toasts and login page; API errors
  are codes translated by the UI.
- Time zone: `TIMEZONE` setting (validated IANA name, `app/core/timezones.py`,
  fallback `Europe/Paris` for upgrades), chosen at the wizard's account step
  (`POST /setup/admin` takes `language` + `timezone`). New plannings without a
  zone get it; existing ones keep theirs.
- PBS address: host-agent route `POST /pve/vm-addresses` (guest agent first,
  then the NIC MACs from `qm config` in `ip neigh`, ping sweep of the bridge
  /24 when missing); `GET /api/v1/setup/pbs/detect?vmid=` keeps the first IP
  where `https://<ip>:8007` answers.
- Agent installer: Proxmox firewall rules for port 8090 (`--no-firewall` /
  `--firewall`), tagged `# pbo-agent` in `host.fw`, removed by `--uninstall`;
  never enables the datacenter firewall.
- Wizard: optional "notifications" step prepared between PBS and Done, hidden
  by `NOTIFICATIONS_STEP_ENABLED = false` (`setup/logic.ts`); the API already
  accepts the step.

## Serials, handoff errors, backup readiness (Phase 4.3)

- Compare a serial seen elsewhere (Proxmox USB list, PBS disk list, planning
  event…) with a disk ONLY through `disk_identity.disk_matches_serial(disk,
  serial)` (stored/canonical/reported serial + aliases; case, spaces, `-`,
  `_`, hex-encoded serials and `WD-` ignored). Proxmox reports `PBOTEST-a`
  for a disk stored as `PBOTESTA`: a verbatim `==` breaks the handoff.
- Handoff failures are `DiskHandoffError` (`code`, clear `detail`,
  `technical`): the run keeps the code as `current_step` (translated by the
  UI) and the technical detail (USB devices seen, with serials) in its log.
- Whether a backup can start is decided server-side:
  `GET /api/v1/external-backups/readiness/{disk_id}` → `ready` + coded
  `reasons` (disk, run active, PVE, host agent, PBS API or PBS agent by
  `PBS_MODE`). The Disks page only displays it; no capability guessing in
  the front. `/system/version` returns `pbs_mode` (Settings shows
  "PBS (API)" in API mode).

## One run per backup, disk states, dashboard & disks pages (Phase 5b)

- **B24 — one run**: a backup with `auto_eject_after_success` ejects inside
  the SAME run (`disk_eject.eject_disk_within_run`): the run stays RUNNING
  through the eject (step 6, same run_id and SSE events), then becomes
  SUCCESS. A failed auto-eject is an ERR line (`auto_eject_failed`) and never
  fails the backup. The manual eject (`eject_dedicated_external_disk`) keeps
  its own run. Planning passes the flag to `run_external_backup` (no second
  eject in `planning_scheduler`).
- **B25 — "ejected" until unplugged**: `handoff_status="ejected"` survives
  agent reports while the disk is still there (`connected=False`, no
  `disk.added`); a report without it (udev remove, or the power-off of the
  eject) publishes `disk.removed` and clears it; the next add makes it usable.
  `disk_events.disk_status` = new | known | ignored | ejected | unplugged |
  rejected (also on `ExternalDiskRead.status`). Readiness reason
  `disk_ejected`. `run_external_backup` refuses with the local readiness
  reasons (`backup_readiness.local_disk_reasons`): **409 with
  `detail.code`, no run created**; the front guards double clicks
  (`src/requestGuard.ts`) and shows a toast.
- Handoff failures: ONE coded ERR line (`handoff_disk_not_plugged`,
  `handoff_usb_*` in `PBO_MESSAGES`), no duplicate stderr merge.
- **B26**: no global banner. `useAppData` queues `notices`
  (`src/notices.ts`, `ApiError` carries `detail.code`), `NoticeToasts` shows
  them as toasts (codes translated via `t.readiness` / `t.disksV2.errors`).
- Approval flow: `POST /disks/{id}/decision` (`approve` needs the disk name
  typed back, `ignore` = until plugged again, `reject` = always,
  `clear`); `external_disks.operator_decision` + `partitions` (Alembic
  `0006`, idempotent). The host agent reports partitions in each disk report
  (`partition_summary`). Guards are unchanged: PBO still refuses to format a
  data filesystem.
- "Run detection again": `POST /disks/rescan` → host agent `/disk/rescan`
  (capability `disk-rescan`, in `ROUTE_ROLES`); codes `rescan_agent_missing`
  / `rescan_agent_outdated` / `rescan_failed`.
- Coverage: the PBS VM (only when `PBS_EXECUTION_VM_ID` is STORED, never the
  default 100) and the CT named like this machine are ignored once as
  `infrastructure` (`services/infrastructure.py`); an existing
  `asset_ignores` row is never overwritten, so a re-include sticks.
  `/overview` returns `infrastructure_ignored`.
- Redesigned pages live in `src/views/` (Tailwind content + language test
  include it) and render OUTSIDE `.pbo-legacy`; legacy pages are wrapped in
  `<LegacyPage>` in `App.tsx`. Pure models: `views/disks/diskModel.ts`,
  `views/dashboard/dashboardModel.ts`, `views/format.ts` (`.ts` imports are
  allowed: `allowImportingTsExtensions`).

## Disk ↔ USB port (Phase 4.4, read before touching the USB passthrough)

- The host agent reports, for each USB disk, its physical USB location read
  in sysfs (`apps/agent/src/agent/usb_location.py`: walk up from
  `/sys/block/<dev>/device` to the USB device with `busnum` + `devpath`) →
  `usb_location` (`port_id` "2-3" = QEMU `host=` syntax, vendor/product,
  USB serial if any, udev `ID_PATH`). Stored on `external_disks.usb_location`
  (+ `usb_location_seen_at`; Alembic `0005`, idempotent because that table is
  still created by `create_all`).
- Handoff order (`disk_handoff.handoff_disk_to_pbs`): ask the agent where the
  disk is NOW (`POST /disk/usb-location`, host role; the disk may have moved
  to another port) → that exact port in `/hardware/usb` (`resolve_usb_device`,
  error `usb_location_not_in_proxmox` if absent, never a guess) → only without
  a location: serial matching, then the "guess" fallback, which excludes every
  non-storage device (known USB class other than 0x00/0x08/0xef/0xff, HID,
  hubs, tablet/keyboard/mouse… by name) and refuses ambiguity
  (`usb_device_ambiguous`). Codes are translated by the UI (`src/handoff.ts`,
  messages must match the API constants — a test checks it).

## Real-time channel (read before touching disk reports, runs or polling)

- Agent (host): `/etc/udev/rules.d/90-pbo-agent.rules` (written by
  `install.sh`, removed by `--uninstall`) starts `pbo-agent-report.service`
  on USB disk add/remove; `sync-state --settle 2` debounces (sleep +
  `udevadm settle`, systemd merges starts while activating) and sends the
  report with `hotplug` (added/removed + serial, diff against
  `/var/lib/pbo-agent/usb-disks.json`, `apps/agent/src/agent/hotplug.py`).
  Timer = 5-minute fallback.
- API: `services/events.py` = in-memory bus (single process) behind
  `publish()` / `EventBus`, ring buffer for `Last-Event-ID`, and the SSE
  stream `GET /api/v1/events` (session cookie, `: ping` every 15 s, stream
  closed after 1 h so the browser reconnects). Event types are a closed set
  (`EVENT_TYPES`): `disk.added|removed|updated`, `agent.online|offline`,
  `run.progress|log|finished`.
- `disk.*` are published by `ingest_agent_disk_report` after the commit
  (`services/disk_events.py`: payload, `reject_reason` = `zero_size` |
  `too_small`, hot-plug history in `activity_events`, category `disk`).
- `run.*` come from SQLAlchemy hooks (`services/run_events.py`): changes of
  `ExternalBackupRun` / `DiskPreparationRun` are collected at flush and
  published after commit (never on rollback), whatever code path wrote them —
  do not publish run events by hand. `agent.online` on heartbeat,
  `agent.offline` from a 30 s watcher started in the lifespan.
- Web: one shared `EventSource` (`src/events.ts`), hook `useEvents()`
  (`src/useEvents.ts`) returning whether the stream is connected. Polling
  loops (`useAppData` run polling, the run log modal) only run while it is
  NOT connected. Pure logic for disk cards / toasts in `src/liveDisks.ts`
  (tested). Toasts: `components/GlobalToasts.tsx`; `/disks?disk=<id>`
  focuses a disk.

## PBS mode: agent vs API (read before touching disk/export/eject code)

- `PBS_MODE` (database setting): `agent` = legacy PBS root agent;
  `api` = PBS REST API (PBS ≥ 3.3, removable datastores). Fresh installs get
  `api`, upgraded installs `agent` (`ensure_pbs_mode` at startup). The
  `Settings` fallback is `agent`.
- **Single switch point**: `get_pbs_agent_client()` (`services/host_agent.py`)
  returns `PBSApiBackend` (`services/pbs_api_backend.py`) in API mode. The
  backend implements the PBS-agent HTTP protocol (same paths, payloads and
  `error_code`s) on top of `PBSClient`. Orchestration code
  (`external_backup_execution.py`, `disk_handoff.py`, `disk_eject.py`) must
  stay mode-agnostic: if it needs something new from "the PBS side", add the
  agent endpoint AND the backend handler.
- Destructive guards for API mode live in `services/pbs_guards.py` (pure
  functions, exhaustively tested): approved disk, ≥ 32 GiB, no system/mounted
  partition, no data filesystem without PBO marker, existing/active datastore
  refused, explicit confirmation. PBO marker = datastore comment
  `pbo:serial=<serial>`. Never call `wipe_disk` / `create_directory_datastore`
  outside `PBSApiBackend._prepare_dedicated`.
- Eject in API mode: idle check → `unmount` UPID followed to the end → only
  then the host agent detaches USB. Timeout → `eject_not_finished` (disk stays
  attached). Agent-prepared (fstab) datastores are `nonremovable` and refused
  in API mode — migration plan in `docs/PBS_API.md`.
- Endpoint/parameter reference and what was verified against the PBS 4.x
  schema: `docs/PBS_API.md`. PBS datastore names are ≤ 32 chars
  (`fit_datastore_name`).
- Agents serve only their role's routes when `AGENT_ROLE=host|pbs` is set
  (`ROUTE_ROLES` in `apps/agent/src/agent/server.py`, enforced in
  `require_agent_token` after the token check). Adding an agent route means
  adding it to `ROUTE_ROLES` (a test fails otherwise).

## Deployment mechanics — LXC `update` and the legacy "Update All"

**LXC install (documented path).** Inside the container, `update`
(`scripts/install/pbo-update.sh`): `pg_dump` to `/var/backups/pbo` → new
version into `/opt/pbo.new` (release asset with pre-built UI, or `git clone`
of `--ref` + temporary Node.js build) → stop → swap `/opt/pbo` ↔
`/opt/pbo.previous` → fresh venv → `create_tables()` + Alembic → start →
`/health`; on failure the previous code and the dump are restored. The host
agent installed by `install.sh` is **not** a git checkout: it is updated by
re-running its install command (it downloads the agent of the running app);
the maintenance "Update All" button does not cover it. Releases: tag `v*` →
`.github/workflows/release.yml` publishes `pbo-<version>.tar.gz` (+ sha256).

**Legacy Docker app VM** — what "Update All" actually does:

Read `docs/MAINTENANCE.md` in full before telling a user their change is
"just a click away" — the update button's coverage differs per component, and
telling the user the wrong thing here has already caused a real production
incident (a live deployment kept running old, unauthenticated agent code for
hours because these gaps weren't obvious).

- **App VM** (api+ui/db): `git pull` + `docker compose up --build -d
  --remove-orphans` recreates the containers; `create_tables()` and the Alembic
  migrations apply schema changes on API startup. Since the UI moved into the
  API image, the old `web` container is removed by `--remove-orphans` and the UI
  is on the API port `8000`: a reverse proxy that pointed at `5173` must be
  repointed — tell the user, the button cannot do it. Plain-HTTP access also
  needs `AUTH_COOKIE_SECURE=false` (Secure session cookie).
- **Proxmox host agent / PBS agent**: `git pull --ff-only` in
  `AGENT_REPO_PATH`, then (if `AGENT_HTTP_SERVICE_NAME` is configured) a
  delayed self-restart of the agent's own `-http.service` — see
  `_maintenance_restart_http_service` in `apps/agent/src/agent/main.py`. This
  only works end-to-end if **both** of these hold on the target machine:
  1. `AGENT_REPO_PATH` points at a real git clone of this repo (not a
     directory populated by `scp`/`rsync` — that has no `.git`, so `git
     fetch`/`pull` fails silently and the agent keeps running whatever code
     was last copied there, no matter how many times the button is clicked).
  2. `AGENT_HTTP_SERVICE_NAME` is set to the actual systemd unit name for that
     machine's agent HTTP service. Without it, the pull can succeed while the
     long-running process still serves old code from memory.
- **App maintenance agent**: has its own equivalent self-restart, already
  wired (`_restart_agent_service` in
  `apps/app-maintenance-agent/src/app_maintenance_agent/main.py`).

Before claiming a change is fully deployed after "Update All": if the change
touches `apps/agent`, confirm the target machine actually satisfies both
conditions above (ask the user, or check `git status`/`.env` on that
machine) rather than assuming the button covered it.

**Never suggest a bare `docker compose -f infra/docker/docker-compose.yml
...` command for the App VM — always include `--env-file .env`.** Without it,
Compose resolves the `${VAR}` references inside the compose file's
`environment:` block using its own default env-file lookup next to the
compose file (`infra/docker/.env`, which doesn't exist), not the real `.env`
at the repo root — silently blanking settings like notifications even though
`env_file: ../../.env` loaded them correctly one line earlier in the same
file. This has already caused a real incident (ntfy config reverting to
defaults after a manual rebuild). `app-maintenance-agent`'s own update flow
already gets this right; a manually-typed command is where it goes wrong.

## Safety notes

- Dedicated PBS datastore preparation can format the selected disk. Treat it as
  destructive until proven otherwise.
- Do not expose ports `8090`, `8091`, `8092` broadly.
- Never change `AUTH_SECRET_KEY` in `/etc/pbo/pbo.env`: it encrypts the stored
  secrets and the agent tokens.
- `.gitattributes` forces LF on `*.sh`/units: a CRLF installer breaks on Linux.
- Never commit `.env` or agent environment files.
- The agents execute host-local commands such as mount, partition, QEMU USB
  attach/detach, and `proxmox-backup-manager`. Read the relevant docs before
  changing those paths.
